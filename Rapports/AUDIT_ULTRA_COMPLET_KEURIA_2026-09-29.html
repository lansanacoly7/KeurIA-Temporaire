Rapport du 29 septembre 2026 · Projet kEur IA (KerIA)

Audit ultra complet : ce qui ne marche pas, ce qui bloque, ce qui manque, ce qui est inutile et ce qui est factice

Écrit pour le responsable du projet. Chaque constat indique comment il a été établi : Vérifié par exécution (test ou script lancé pendant l'audit), Mesuré, Lecture du code, Déduit (non exécuté).

Verdict : la plateforme n'est pas prête pour des enfants réels. Le socle (authentification, cloisonnement des écoles, tests serveur) est solide, mais deux fonctions clés sont cassées (parcours des 10–15 ans, temps d'écran accordé par le parent), un endpoint anonyme permet de deviner le mot de passe d'un parent, le serveur invente des réussites dans les notifications des parents, le classement est falsifiable, et le site promet une conformité RGPD qu'il ne peut pas tenir.

2. Méthode et limites

  • Exécuté : 246 tests backend, manage.py check --deploy avec réglages de production simulés, sondes de test jetables (session réelle, requêtes anonymes, comptage de requêtes SQL sur une école de démonstration de 212 élèves), tsc, ESLint sur tout app/, build Next.js, graphe d'imports du frontend, lecture directe de l'index Git.
  • Non réalisé : npm audit et pip-audit (pas d'accès réseau), test de charge, tests en navigateur réel, appel réel à l'API Anthropic, envoi SMTP réel. Historique Git non fouillé (git absent de la machine).
  • Plusieurs sessions modifient ce dépôt en parallèle (la page d'accueil a été remplacée pendant l'audit) : les numéros de ligne peuvent bouger.
  • Taille du projet : backend 9 266 lignes (+3 057 de tests, 36 migrations), frontend 33 425 lignes TypeScript + 12 278 lignes CSS, 42 pages.

3. Ce qui ne marche pas ou peut bloquer

Défauts fonctionnels et techniques, du plus grave au plus mineur.

P0 BUG-01

Les parcours 10–12 et 13–15 ans sont inaccessibles aux élèves

  • Lecture du code frontend/app/dashboard/[[...slug]]/page.tsx:20 fixe assignedAge = "7-9" pour tout le monde, et DashboardClient.tsx:420-421 verrouille l'âge (ageLocked = isLearner, selectAge n'accepte que assignedAge).
  • Lecture du code Le serveur connaît pourtant l'âge : LearnerProfile.age_track est synchronisé avec la classe (sync_learner_track) et GET /api/progress le renvoie (ageTrack). Aucun écran ne l'utilise.

Impact. Un élève de CM2 ou de 3e voit le parcours 7–9 ans. 24 modules (parcours 10–12 et 13–15) et leur contenu sont hors d'atteinte pour les élèves.

Correction. Lire ageTrack côté serveur dans la page et le passer à assignedAge ; ajouter un test avec un élève de chaque parcours.

P0 BUG-02

Le parent ne peut pas accorder de temps d'écran supplémentaire

  • Vérifié par exécution Avec une vraie session parent (cookie, comme un navigateur), POST /api/progress/parental-limits/unlock {action: respond_request} répond 400 « Compte enfant introuvable. » et la demande reste pending.
  • Lecture du code La vue déclare authentication_classes = [] : request.user est toujours anonyme, donc toutes les branches « parent connecté » (approuver, accorder des minutes) sont mortes.
  • Lecture du code Les 3 tests existants utilisent force_authenticate, qui contourne ce défaut : ils passent alors que la fonction est cassée.

Impact. La fonctionnalité phare du contrôle parental (« +15 min ») ne fonctionne pas en production.

Correction. Authentifier la vue par session ; séparer clairement l'endpoint parent de l'endpoint enfant ; écrire les tests avec une vraie session.

P1 BUG-03

Réglages de temps d'écran : erreur 500 et valeurs absurdes acceptées

  • Vérifié par exécution dailyLimitMinutes="abc" → 500 (ValueError dans ParentalLimitsView.post). -50 minutes et une heure de coucher « 25:99 » sont acceptés et enregistrés.

Impact. Une saisie invalide plante l'API ; des valeurs absurdes désactivent silencieusement la règle.

Correction. Passer par un sérialiseur avec bornes (0–1 440 min, format HH:MM).

P1 BUG-04

Le déverrouillage parental falsifie les statistiques d'usage

  • Vérifié par exécution Après un déverrouillage, DailyUsage.minutes est passé de 40 à 25 : le code soustrait 15 minutes aux minutes réellement jouées.

Impact. Les minutes affichées au parent, les moyennes du dossier pédagogique et les alertes sont fausses.

Correction. Ne jamais modifier l'usage mesuré : stocker un crédit de temps distinct (modèle + expiration en base).

P1 BUG-05

Lire la progression coûte 66 requêtes SQL et écrit en base

  • Mesuré Élève connecté : GET /api/progress = 66 requêtes ; POST /api/progress = 30 requêtes (école de 212 élèves).
  • Lecture du code compute_badges fait un get_or_create par badge (×12) et crée LearnerStats, EarnedReward, jours de connexion… à chaque lecture.

Impact. Appelé à chaque chargement du tableau de bord : charge SQL et écritures inutiles, surtout avec des classes entières connectées en même temps.

Correction. Calculer les badges en mémoire à la lecture et n'écrire que lors d'un événement réel ; mettre en cache le total d'XP.

P1 BUG-06

Le lint est inutilisable et le code ne passe pas ESLint

  • Lecture du code npm run lint lance bash scripts/sites-env.sh (dépend de flock, GNU timeout, sha256sum : Linux uniquement) — échoue sous Windows.
  • Mesuré ESLint lancé directement : 458 erreurs et 252 avertissements dans 185 fichiers (330 apostrophes non échappées, 127 <img>, 113 variables inutilisées, 59 any, 30 setState dans des effets, 14 fonctions impures).

Impact. Aucun garde-fou qualité : aucune intégration continue ne pourrait passer.

Correction. Remplacer le script de lint, corriger ou justifier les règles, brancher une CI.

P2 BUG-07

Le verrouillage horaire n'est appliqué nulle part côté serveur

  • Lecture du code isLocked est calculé dans GET /api/progress/parental-limits mais aucun autre endpoint ne le vérifie. Seule une surcouche du navigateur (ScreenTimeManager, 1 187 lignes, drapeau sessionStorage) bloque l'écran.

Impact. Un enfant contourne la limite en vidant le stockage du navigateur ou en appelant l'API directement.

Correction. Faire refuser par le serveur les écritures (progression, jeux, chat) pendant une période verrouillée.

P2 BUG-08

Dérogations et anti-bruteforce dépendent d'un cache mémoire par processus

  • Lecture du code settings.py ne définit pas CACHES (cache mémoire local). Y sont stockés : temp_unlock_*, les compteurs de verrouillage de connexion (login-fail:*) et la limitation de débit. Le code le reconnaît (« configurer un cache partagé »).

Impact. Avec plusieurs workers, une dérogation accordée par le parent est invisible pour l'enfant, et le blocage des tentatives de connexion est contournable.

Correction. Configurer Redis (ou persister les dérogations en base).

P2 BUG-09

Unicité inopérante des règles globales du foyer

  • Déduit (non exécuté) UniqueConstraint(parent, child) ne protège pas quand child est NULL (règle « tous les enfants ») : le SQL traite les NULL comme distincts.

Impact. Doublons possibles ; update_or_create peut lever MultipleObjectsReturned.

Correction. Contrainte partielle (condition=Q(child__isnull=True)).

P2 BUG-10

Échec d'envoi d'e-mail invisible : l'utilisateur reste bloqué

  • Lecture du code send_code_email avale toute exception (journalisée seulement) et l'inscription répond « Un code a été envoyé » quelle que soit l'issue. SMTP Gmail (587, limite ~500/jour) est appelé de façon synchrone dans la requête.

Impact. Si Gmail refuse ou est lent, le parent attend un code qui n'arrivera jamais ; latence ajoutée à l'inscription.

Correction. File d'envoi asynchrone, réponse honnête en cas d'échec, fournisseur transactionnel dédié.

P3 BUG-11

Fuseau horaire implicite

  • Lecture du code TIME_ZONE = 'UTC' et mélange de timezone.now().date() / localdate() selon les modules.

Impact. Sans conséquence à Dakar (UTC+0), fragile pour un déploiement dans un autre fuseau (séries de connexion, jour d'usage).

Correction. Utiliser localdate() partout et fixer TIME_ZONE explicitement.

4. Sécurité et vie privée

Failles exploitables et engagements non tenus vis-à-vis des mineurs.

P0 SEC-01

Déverrouillage parental anonyme : bruteforce illimité et spam de notifications

  • Vérifié par exécution Sans aucune connexion, 30 essais de mot de passe parent sur un childId → 30 réponses 401, aucun blocage (pas de limitation, LoginLockout non utilisé).
  • Vérifié par exécution Avec le bon mot de passe et sans être connecté → 200 + cookie de session de l'enfant.
  • Vérifié par exécution 50 requêtes anonymes request_time → 50 notifications créées chez le parent (les identifiants d'enfant sont des entiers séquentiels).

Impact. Le mot de passe d'un parent peut être deviné sans limite ; n'importe qui peut inonder les parents de notifications.

Correction. Exiger la session de l'enfant (jamais un childId du client), limiter le débit et verrouiller comme la connexion.

P1 SEC-02

Le classement et l'XP sont falsifiables en quelques secondes

  • Vérifié par exécution GET /api/curriculum/lessons/p1-1/, public, renvoie questions[].correct et activity.correct (136 leçons avec contenu en base).
  • Lecture du code Le serveur n'exige aucune preuve de complétion : POST /api/progress {lessonId} suffit (l'XP est fixée par le serveur depuis mon correctif, mais reste attribuée sans vérification).

Impact. Un script valide les 176 activités du catalogue et prend la 1re place ; tout classement ou bilan devient sans valeur pédagogique.

Correction. Valider les réponses côté serveur, ne plus exposer correct, limiter le débit et exiger une durée minimale par activité.

P1 SEC-03

Vie privée des mineurs : promesses non tenues et absence de cadre RGPD

  • Lecture du code La landing affirme « RGPD », « aucune donnée n'est cédée à des tiers », « 100% sécurisé & sans pub », « Conforme aux exigences éducatives : développé en partenariat… ».
  • Lecture du code Or : le texte écrit par l'enfant à Palou part chez Anthropic ; chaque visiteur charge des polices Google (IP transmise), le modèle MediaPipe depuis storage.googleapis.com et des scripts depuis cdn.jsdelivr.net ; la webcam est utilisée (AdvancedGames.tsx:164).
  • Lecture du code Aucune page CGU / confidentialité / mentions légales / consentement parental (recherche dans app/), aucun endpoint de suppression ou d'export de compte.

Impact. Risque juridique réel (RGPD, protection de l'enfance) et atteinte à la confiance des familles et des écoles.

Correction. Pages légales, consentement parental, suppression/export, auto-héberger polices et modèles, contrat de traitement avec les sous-traitants, corriger les affirmations de la landing.

P1 SEC-04

Secret réel dans backend/.env

  • Vérifié par exécution backend/.env contient une adresse Gmail et un mot de passe d'application réels, avec DEBUG=True. Le fichier n'est pas suivi par Git (index vérifié) et aucun secret n'apparaît dans les 14 gros fichiers texte suivis.
  • Déduit (non exécuté) L'historique Git n'a pas pu être fouillé (git non installé) : vérifier avec git log --all -- backend/.env.

Impact. Si le fichier a déjà été partagé (archive, capture, autre machine), le compte de messagerie est compromis.

Correction. Révoquer/régénérer le mot de passe d'application ; utiliser un gestionnaire de secrets.

P2 SEC-05

Comptes enfants : e-mail libre marqué « vérifié »

  • Vérifié par exécution Un compte enfant créé par un parent a email_verified = True sans aucun contrôle (create_user par défaut).

Impact. Un parent peut créer un compte avec l'adresse d'un tiers et l'empêcher de s'inscrire ; l'adresse n'est jamais prouvée.

Correction. Identifiant interne sans e-mail pour les enfants, ou vérification par le parent.

P2 SEC-06

Un enseignant sans école est rattaché automatiquement à une autre école

  • Lecture du code accounts/views.py (profile_payload et start_session, code dupliqué) attache tout enseignant sans école à l'école de slug les-baobabs (codé en dur) ou à School.objects.first(), avec écriture en base pendant un simple GET /api/profile.

Impact. Accès à la fiche et aux missions d'une école qui n'est pas la sienne ; comportement dépendant des données de démonstration.

Correction. Refuser la connexion tant qu'aucune école n'est affectée ; supprimer le slug de démonstration du code métier.

P2 SEC-07

Pas d'en-têtes de sécurité web côté Next.js

  • Lecture du code next.config.ts ne définit ni CSP, ni X-Frame-Options, ni Referrer-Policy, ni Permissions-Policy : les pages HTML sont servies par Next, pas par Django.
  • Vérifié par exécution manage.py check --deploy (simulation production) : W005 (HSTS sous-domaines), W009 (clé), W021 (preload). HSTS réglé à 3 600 s seulement.

Impact. Clic-jacking possible, pas de défense en profondeur contre l'injection de scripts.

Correction. Ajouter les en-têtes dans next.config.ts ; monter HSTS après validation HTTPS.

P2 SEC-08

Le verrouillage de connexion permet de bloquer le compte d'un tiers

  • Lecture du code 5 échecs sur un e-mail = 15 minutes de blocage, par e-mail, sans preuve de propriété ; compteur en mémoire locale (voir BUG-08).

Impact. Déni de service ciblé contre un parent ou un enseignant précis.

Correction. Verrouillage progressif par couple (IP, compte), captcha après quelques échecs.

P2 SEC-09

Flux SSE non utilisé qui monopolise un worker

  • Lecture du code SSENotificationsView boucle sleep(1) pendant 5 minutes par connexion. Son commentaire indique lui-même qu'il n'est pas utilisé par le frontend.

Impact. Quelques connexions suffisent à saturer les workers WSGI.

Correction. Supprimer la route.

P3 SEC-10

Hachage : PBKDF2-SHA1 accepté, Argon2/Bcrypt listés sans bibliothèque

  • Lecture du code PASSWORD_HASHERS contient PBKDF2SHA1, Argon2, BCryptSHA256 ; argon2 et bcrypt ne sont pas installés.

Impact. Surface inutile ; un ancien hash faible reste valide.

Correction. Ne garder que PBKDF2 (ou installer Argon2 et l'utiliser en premier).

P3 SEC-11

Contrats d'API trompeurs pour un visiteur anonyme

  • Lecture du code GET /api/profile renvoie un faux profil « Explorateur / parent » ; POST /api/progress/tutorial-complete répond success à un anonyme ; ProgressView et ParentalLimitsView sont en AllowAny.

Impact. Risque d'erreurs d'intégration et de fausses réussites.

Correction. Renvoyer 401 et utiliser IsAuthenticated.

P3 SEC-12

Deux définitions de l'administrateur

  • Lecture du code Rôle Django admin et liste d'e-mails KEUR_ADMIN_EMAILS lue côté Next (admin-auth.ts) qui active le mode aperçu administrateur.

Impact. Confusion de privilèges entre deux sources de vérité.

Correction. Une seule source : le rôle serveur.

P3 SEC-13

Valeurs CORS/CSRF de développement appliquées si l'environnement est incomplet

  • Lecture du code Sans CORS_ALLOWED_ORIGINS, le code retombe sur localhost:3000/3001/5173 (et CSRF_TRUSTED_ORIGINS en hérite), même hors DEBUG.

Impact. Une production mal configurée démarre sans alerte.

Correction. Lever une erreur au démarrage si DEBUG=False et variable absente.

P3 SEC-14

Déconnexion incomplète sur tablette partagée

  • Lecture du code signOut efface 6 clés fixes ; les clés par utilisateur (événements vus, séries, erreurs, streaks) restent dans localStorage.

Impact. Traces d'un élève visibles pour le suivant sur un appareil de classe.

Correction. Purger toutes les clés préfixées keria_.

5. Code factice, simulé ou trompeur

Ce qui affiche ou promet quelque chose qui n'existe pas réellement.

P0 FAKE-01

Le serveur fabrique de fausses notifications pour les parents

  • Vérifié par exécution ParentNotificationsView.get (« Alimentation des exploits… ») insère en base des notifications inventées tant que le parent en a moins de 7. Un parent neuf dont l'enfant n'a aucune activité passe de 0 à 6 notifications à la 1re lecture : « Niveau 2 (Éclaireur de l'IA) », « Série de 5 jours », « Concept maîtrisé : Réseau de neurones », « 3e place au classement », « Titre Explorateur des Étoiles », « 4 jours d'inactivité ».
  • Lecture du code Elles sont attribuées au vrai prénom de l'enfant et antidatées (created_at modifié).

Impact. Le parent est trompé sur le travail et le comportement de son enfant : c'est le pire cas de donnée factice de la plateforme.

Correction. Supprimer ce bloc, purger les lignes déjà créées (repérables à leurs textes), ne notifier que des événements réels.

P1 FAKE-02

Réglages parentaux sans aucun effet, dont une « double authentification » inexistante

  • Lecture du code emailNotifs, pushNotifs, weeklyReport, twoFactor sont enregistrés puis jamais lus. Les seuls e-mails envoyés sont le code de vérification et le code de réinitialisation. Aucun push, aucun rapport hebdomadaire, aucun 2FA.

Impact. Le parent croit activer des protections et des rapports qui n'existent pas.

Correction. Implémenter ou retirer les interrupteurs de l'interface.

P2 FAKE-03

Titres de leçons codés en dur dans les notifications

  • Lecture du code LESSON_TITLES_MAP (7 titres) sert de source dans enrich_notification alors que 136 titres existent en base.

Impact. Titres obsolètes ou faux dès que le catalogue évolue.

Correction. Lire Lesson.title.

P2 FAKE-04

Landing : chiffres, badges et démonstration non reliés à des données

  • Lecture du code Métriques « 12+ », « 100% », badge « RGPD », exemples « 420 XP » / « Niveau 3 débloqué (+150 XP) » et conversation Palou scriptée (« 10 000 photos de chats ») — illustrations statiques présentées comme des faits.

Impact. Promesses invérifiables (voir SEC-03).

Correction. Retirer ou sourcer les chiffres ; étiqueter les démonstrations.

P2 FAKE-05

Catalogue pédagogique dupliqué en quatre endroits

  • Lecture du code Base de données (Lesson/LessonContent), lms-data.ts, curriculum-10-12.ts / curriculum-13-15.ts, pilotLessons dans DashboardClient.tsx. L'API du catalogue existe mais curriculum-api.ts n'est importé par aucun écran.
  • Vérifié par exécution Aujourd'hui les copies coïncident (34 modules, titres et XP identiques) ; un test garde désormais paliers, XP et badges.

Impact. Toute modification de contenu doit être faite quatre fois ; dérive garantie à terme.

P2 FAKE-06

XP annoncés mais inobtenables, pages « en construction »

  • Lecture du code « Défi de la semaine » (+45 / +75 / +100 XP) affiché dans l'arcade sans aucun mécanisme pour le gagner ; onglet Arcade « Page en construction » ; niveaux « Bientôt disponible ».

Impact. L'enfant poursuit une récompense qui n'existe pas.

Correction. Implémenter ou retirer.

P3 FAKE-07

Résidus factices dans la configuration et la documentation

  • Lecture du code frontend/README.md est un gabarit vide (« npm install keur-ia ») ; <meta codex-preview> dans layout.tsx ; tests/rendered-html.test.mjs vestige non exécuté (le README le reconnaît).

P3 FAKE-08

Rôle « enfant » fantôme

  • Lecture du code 28 occurrences de role === "enfant" dans le frontend ; ce rôle n'existe pas côté serveur (admin, admin_ecole, parent, enseignant, eleve).

P3 FAKE-09

Données de démonstration liées à la logique métier

Impact. Dépendance cachée à des données de test.

Correction. Isoler la démo dans des fixtures et retirer le slug du code.
