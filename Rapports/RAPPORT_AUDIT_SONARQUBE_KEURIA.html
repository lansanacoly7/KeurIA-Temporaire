2. Sécurité — 49 vulnérabilités

Analyse qualifiée : 4 remontées exigent une action, 45 sont des faux positifs contextuels.

2.1 — Remontées à traiter

Clé secrète Django en dur Blocker

backend/keuria/settings.py:26 — règle secrets:S6687

Le littéral 'django-insecure-keuria-dev-only' est présent dans le code source comme valeur de repli de SECRET_KEY.

Risque réel : faible. Le garde-fou est correctement implémenté — en l'absence de SECRET_KEY et hors DEBUG, le démarrage lève ImproperlyConfigured. Le repli n'est donc jamais atteint en production.

Action : remplacer le littéral par get_random_secret_key() généré au runtime. Le secret restant dans l'historique Git, il doit être considéré comme révoqué et ne jamais être réutilisé.

Mot de passe de démonstration Major

backend/apps/scolaire/management/commands/seed_demo_school.py:42 — règle python:S2068

Constante DEMO_PASSWORD = 'Demo-Keuria-2026' utilisée pour peupler l'école de démonstration « Les Baobabs ».

Risque réel : faible et acceptable dans un script de seed. Le point de vigilance n'est pas le littéral mais l'exécutabilité de la commande : si seed_demo_school peut être lancée sur l'instance de production, elle y crée des comptes dont le mot de passe est public dans le dépôt.

Action : garder le littéral mais verrouiller la commande (refus explicite si DEBUG=False), ou lire le mot de passe depuis l'environnement avec repli de développement.

Exécution dynamique de code Critical ×2

frontend/app/dashboard/DashboardClient.tsx:3157 — règle typescript:S1523

Appel à new Function("move","turn","center","say","wait", generated) pour exécuter le JavaScript produit par l'atelier Blockly.

Risque réel : faible en l'état. Le code exécuté est généré par javascriptGenerator à partir des blocs assemblés par l'enfant lui-même, côté client uniquement, et les cinq primitives injectées sont inoffensives (déplacement, rotation, message).

Action : aucune correction immédiate. En revanche, ce point devient bloquant si les projets Blockly deviennent un jour partageables ou persistés entre élèves : un programme reçu d'un tiers serait alors exécuté sans isolation. À tracer comme dette de sécurité conditionnelle.

3.1 — Accessibilité clavier : 72 occurrences

Des gestionnaires onClick / onMouseOver sont posés sans onKeyDown, role ni tabIndex correspondants. À cela s'ajoutent, côté code smells, 49 occurrences de S6848 (gestionnaire interactif sur un élément DOM non interactif — typiquement un <div> cliquable) et 18 occurrences de S6819 (rôle ARIA là où une balise sémantique existe).

Ce lot de ~140 remontées est le plus structurant du rapport. Kër IA est une plateforme éducative destinée à des enfants et à un déploiement en milieu scolaire : la navigation entièrement au clavier et la compatibilité lecteur d'écran relèvent moins de la qualité de code que de la conformité d'usage et des exigences d'accessibilité attendues d'un outil scolaire. Elles conditionnent par ailleurs l'accès aux élèves en situation de handicap moteur.

Approche recommandée : plutôt que 140 corrections ponctuelles, introduire deux ou trois composants partagés (<Pressable>, <Card clickable>) encapsulant une fois pour toutes role="button", tabIndex={0} et le couple onClick/onKeyDown, puis substituer les <div> cliquables. L'essentiel des 140 issues tombe mécaniquement.

3.2 — Condition morte

Ternaire sans effet S3923

frontend/app/dashboard/AdvancedGames.tsx:937

Dans le style du bouton « Lancer le dialogue », la propriété color s'évalue à (!promptData.lieu || !promptData.sujet) ? "#FFF" : "#FFF" — les deux branches retournent la même valeur.

Action : remplacer par color: "#FFF". À noter que l'état désactivé du bouton combine un fond #E5E7EB avec un texte blanc, soit un contraste insuffisant — à rapprocher des 34 remontées css:S7924 (§ 4).

Rollback d'état React fragile S6443 ×3

DashboardClient.tsx:636, DashboardClient.tsx:652, DashboardContext.tsx:129

Le motif est un rollback optimiste : setProgress(next) puis, si POST /api/progress échoue, setProgress(progress) pour restaurer l'état antérieur.

Le comportement est correct aujourd'hui — progress est la valeur de closure capturée avant la mise à jour, donc bien l'état précédent. Mais le motif est fragile : toute évolution de la fonction (await supplémentaire, mise à jour concurrente, passage en useTransition) le casse silencieusement, et le rollback restaurerait alors un état périmé.

Action : capturer explicitement l'état avant mutation (const previous = progress;) et restaurer previous, ce qui rend l'intention lisible et lève la remontée.

Conséquence directe du style d'écriture très dense du frontend (styles inline conditionnels, JSX sur une seule ligne). Chaque occurrence est bénigne, mais le cumul est le premier facteur d'illisibilité du code.

Action : faible priorité en correction isolée. Ces ternaires disparaissent naturellement lors du découpage des gros fichiers (§ 5) et de l'extraction des styles inline vers des classes CSS ou des variantes de composants.

168 props non readonly Correction mécanique

Les interfaces de props React ne déclarent pas leurs champs en lecture seule. Aucun impact fonctionnel, mais la règle protège contre les mutations accidentelles de props.

Action : corrigeable en masse par codemod (type Props = Readonly<{...}>). Gain immédiat de ~17 % du volume de smells pour un risque de régression nul.

6. Couverture de tests, duplication & documentation

Indicateurs complémentaires de robustesse.

Couverture de tests 33,3 % projet

La couverture a été instrumentée et transmise au scanner dans le cadre de cet audit (coverage.py → Cobertura XML → sonar.python.coverage.reportPaths). La suite compte 153 tests, tous passants.

Le 33,3 % global est une moyenne diluée et doit être lu par périmètre : le backend est solidement couvert, le frontend ne l'est pas du tout. C'est la ventilation ci-dessous qui porte l'information, pas le chiffre agrégé.

Backend Django 82,1 % — bon

backend/apps : 82,3 % (599 lignes non couvertes sur 3 389). backend/keuria : 74,7 % (22 sur 87).

Niveau conforme aux attentes pour une application métier. Les deux seuls modules entièrement découverts sont les commandes de management seed_demo_school.py (144 lignes) et create_school_admin.py (33 lignes) — attendu pour des scripts d'amorçage, et sans enjeu.

Points réellement à renforcer : scolaire/services/imports.py (65,5 % — le plus faible du code métier, et par ailleurs 4e plus complexe du projet), progress/views.py (73,7 %) et scolaire/services/ecole.py (80,8 %, 69 lignes découvertes).

Frontend Next.js 0 % — angle mort

5 091 lignes à couvrir, 5 091 non couvertes. Le dépôt ne contient qu'un seul fichier de test frontend (frontend/tests/rendered-html.test.mjs), sans instrumentation de couverture.

C'est le déséquilibre majeur du projet : le frontend concentre 100 % des bugs, 96 % de la dette technique et la totalité de la complexité critique (§ 5), et c'est précisément la partie dépourvue de filet de sécurité. Les deux fichiers à refondre — KidsLessonPlayer79.tsx et DashboardClient.tsx — devraient être refactorés sans aucun test de non-régression.

Action : cet enchaînement conditionne le chantier P3. Écrire les tests avant le découpage ne sera pas praticable sur des fonctions à 597 de complexité ; l'ordre réaliste est d'extraire d'abord la logique pure (machine à états de progression, calcul d'XP, sélection d'exercice) dans des modules testables, puis de la couvrir, et seulement ensuite de réorganiser la couche de présentation.

Duplication 2,3 % — bon

68 blocs dupliqués pour 2,3 % des lignes, en deçà du seuil usuel de 3 %. Le résultat est d'autant plus satisfaisant que les fichiers de données statiques (curriculum-*.ts, lms-data.ts, daily-plan.ts) ont été exclus du calcul : leur répétition structurelle est intentionnelle et aurait faussé la mesure à la hausse.

Action : aucune. Indicateur à maintenir.

Densité de commentaires 3,8 %

Faible au regard des 40 516 lignes analysées, et particulièrement problématique sur les fichiers à forte complexité où aucun commentaire n'oriente la lecture.

Action : ne pas traiter comme un objectif chiffré. L'effort de documentation doit cibler les points chauds du § 5 — et le découpage de ces fichiers rend de toute façon une part des commentaires inutile en explicitant l'intention par la structure.

Security Review A — 0 hotspot

Aucun security hotspot détecté, c'est-à-dire aucun point nécessitant une revue humaine pour arbitrer un risque contextuel. Note A.

Ce résultat est cohérent avec le travail de sécurisation documenté dans le rapport d'audit global (plan d'authentification T01–T17).

8. Reproductibilité de l'analyse

Configuration versionnée et procédure de relance.

Périmètre retenu

La configuration est versionnée dans sonar-project.properties à la racine du dépôt. Sources analysées : backend/apps, backend/keuria, frontend/app, frontend/lib, frontend/worker.

Couverture : sonar.python.coverage.reportPaths=backend/coverage.xml. Le périmètre mesuré et ses exclusions (tests, migrations, wsgi/asgi, manage.py) sont définis dans backend/.coveragerc, également versionné. Aucune couverture frontend n'est produite à ce jour.

Exclusions : node_modules, __pycache__, migrations, .next, dist, public, examples, fichiers minifiés et répertoires de tests (déclarés séparément en sonar.tests). Les fichiers de travail de la racine (old_dashboard*.tsx, diffs, scripts d'extraction) sont volontairement hors périmètre : ils auraient introduit du bruit et une duplication artificielle.

Relancer l'audit

# 1. Démarrer le serveur SonarQube (port 9000)
docker start keuria-sonarqube

# 2. Générer la couverture backend (voir §6)
#    pytest-cov n'est pas installé : on passe par coverage.py, déjà présent.
#    Le périmètre et les exclusions sont figés dans backend/.coveragerc
cd backend
python -m coverage run -m pytest
python -m coverage xml          # → backend/coverage.xml
cd ..

# 3. Lancer le scanner depuis la racine du dépôt
sonar-scanner \
  -Dsonar.host.url=http://localhost:9000 \
  -Dsonar.token=$SONAR_TOKEN

# 4. Consulter le tableau de bord
open http://localhost:9000/dashboard?id=keuria-v2
Piège de configuration à connaître pour l'intégration continue. La résolution des chemins du rapport Cobertura par SonarQube est sensible à la façon dont coverage.py écrit ses balises <source>. Trois configurations ont été écartées avant d'aboutir :
• source = apps,keuria → deux racines, et les __init__.py présents dans chacune deviennent ambigus (« the file exists in several source ») ;
• ajout de relative_files = True → produit une balise <source> vide qui fait échouer la résolution de 74 fichiers, silencieusement exclus de la mesure ;
• source = . sans relative_files → une racine absolue unique et des chemins préfixés (apps/…, keuria/…) : résolution complète, zéro erreur.

C'est cette dernière forme qui est figée dans backend/.coveragerc. En CI, vérifier systématiquement que le log du scanner ne contient aucun Cannot resolve the file path : l'analyse reste en succès et le chiffre de couverture s'affiche malgré tout, mais amputé des fichiers non résolus — donc faux sans aucun signal d'alerte.
Note d'exploitation. L'analyse a été menée sur une instance SonarQube Community locale (conteneur Docker keuria-sonarqube), avec un jeton d'analyse à usage unique. Ce jeton et le mot de passe administrateur de l'instance sont locaux à la machine d'audit et ne figurent pas dans ce rapport ni dans le dépôt. Pour une intégration continue, provisionner un jeton dédié en variable d'environnement SONAR_TOKEN côté CI, et ne jamais le committer.
